## 1. 📌 Split 정책 개요 및 원칙

본 문서는 교과 7에서 전수 검수를 마친 900장의 데이터를 교과 8 개발용(`Train`, `Validation`, `Frozen Test`)과 교과 14 연결용(`Bridge Holdout`)의 4가지 역할로 나누는 분할 기준을 정의합니다.

### 1.1 핵심 분할 원칙
1. **회차(Session) 누수 방지**:
   - 같은 김치, 같은 조명, 같은 시간대에 연속 촬영된 유사 사진들이 서로 다른 Split에 섞여 들어가는 **Data Leakage를 방지**하기 위해, 개별 사진 단위가 아닌 **촬영 묶음(`capture_group`) 단위로 통째로 배정**합니다.
2. **희귀 클래스·하위 모습 보장 (통제된 예외 3건: G00 · G12 · G09)**:
   - Class 6(파·고추)는 전체 900장 중 G00(50장) 묶음에 사실상 전량 몰려 있습니다. 완전 묶음 단위 분할 시 Val/Test/Bridge에서 Class 6 평가가 불가능해지므로, **G00 묶음 50장에 한해 시간순 연속 블록 분할 예외를 적용**합니다.
   - (`kimchi_v2`) 마른 잎(Class 0)·작은 반점 갈변(Class 5)은 G12·G13 에만 있어 Train 에 그 모습이 없었습니다. **G12 75장의 가운데 배치 25장을 Train** 으로 보내는 두 번째 예외를 적용합니다 (5장 참고).
   - (`kimchi_v4`) 라벨 개정 후 갈변의 81% 가 G09 에 몰려 Val 갈변이 8개뿐이라 **G09 마지막 배치 25장을 Val** 로 보냅니다 (5.2 참고).
   - 원칙: **각 Class 의 주요 모습(하위 유형)이 Train 에 있어야 한다.** 평가 역할에만 있는 모습은 모델이 배울 수 없어 성능이 아니라 데이터 구성을 재게 됩니다.
3. **교과 14 실전 검사 환경 정합성 (이물 단독 150장 처리)**:
   - G17(이물 단독 150장)은 동일한 배경에서 연속 촬영되어 사진 간 유사도가 매우 높으므로, 여러 Split으로 쪼갤 경우 누수 위험이 큽니다.
   - 또한 교과 14는 컨베이어 벨트 위의 '김치+이물'을 검사하는 실전 프로젝트이므로, **G17(150장)은 모델의 순수 객체 표현력 학습을 위해 Train에 전량 배정**하고, Val / Test / Bridge는 100% '김치+이물' 실전 장면으로만 구성합니다.

## 2. 🔍 촬영 묶음(`capture_group`) 정의 및 유사도 검증

### 2.1 묶음 분리 기준
* **분리 규칙**: 파일명 타임스탬프(`YYMMDD_HHMMSS`) 기준 **촬영 간격이 5분(300초)을 초과하는 지점**에서 분리
* **결과**: 총 **18개 묶음 (`G00` ~ `G17`)** 생성

### 2.2 이미지 유사도 (dHash) 검증 결과
* 재현: `python scripts/02_audit_subject7_final.py` → `reports/leakage_check.csv`, `reports/capture_group_summary.csv` (코드: `src/leakage_check.py`)
* dHash 는 사진을 17×16 흑백으로 줄여 만든 256bit 지문입니다. 두 지문의 다른 bit 수(0~256)가 작을수록 비슷한 사진이며, **10 이하를 "거의 같은 사진"**으로 봅니다.
* 900장 전체(약 40만 쌍)를 비교한 결과:

| 지표 | 값 | 의미 |
|---|---:|---|
| 완전히 같은 사진 쌍 (거리 0) | **0** | 중복 파일·이름만 다른 동일 사진 없음 |
| 거의 같은 사진 쌍 (거리 ≤ 10) | 88 | **88쌍 모두 같은 묶음 안** (전부 G17 이물 단독) |
| 서로 다른 묶음 사이의 거의 같은 쌍 | **0** | 묶음 단위로 나누면 사진 수준 누수 없음 |
| 평균 거리: 같은 묶음 / 다른 묶음 | 74.8 / 111.8 | 같은 묶음 사진이 더 비슷함 → 시간 묶음이 실제 촬영 묶음과 맞음 |

* 김치 묶음(G00~G16)은 묶음 **안** 사진끼리의 거리 중앙값이 97~112 로, 서로 다른 묶음 사이(평균 112)와 비슷합니다. 김치 사진은 같은 회차 안에서도 배치가 매번 다릅니다. 반대로 G17 은 배경이 같아 묶음 안 중앙값이 23 으로 매우 가깝습니다.
* Class 6 묶음(`G00`) 내부 사진끼리의 차이는 중앙값 104로, 서로 다른 묶음 간의 평균 차이(112)와 유사하여 **G00 50장의 배치와 형태가 모두 상이함(육안 및 수치 검증 완료)**을 확인했습니다.
* 한계: dHash 는 좌우 반전·회전 사진과 같은 실물 이물의 재촬영은 잡지 못합니다. 교과 7 FINAL 에는 변형(Augmentation) 사진을 넣지 않았습니다.

### 2.3 원래 train / validation 구분을 Split 에 쓰지 않은 이유
교과 7 FINAL 은 회사가 나눠 준 원래 구분(`원래 split`: train 720장 / validation 180장)을 보존하고 있습니다. 가이드(11.2)는 원래 `Dataset 2 / validation` 을 Validation 우선 후보로 검토하도록 하지만, **그대로 쓰지 않았습니다.**

* **근거**: 18개 촬영 묶음 중 **17개 묶음에 원래 train 과 원래 validation 사진이 함께 들어 있습니다.** (나머지 `G01` 은 1장뿐인 묶음)
  - 예: `G17`(250513, 약 43분 연속 촬영) = 원래 train 120장 + 원래 validation 30장
  - 예: `G12`(250424 13:12~14:01) = 원래 train 59장 + 원래 validation 16장
* 즉 원래 구분은 **같은 촬영 회차 안에서 사진 단위로 나눈 것**으로 보입니다. 같은 김치·조명·시간대 사진이 Train 과 Validation 에 동시에 들어가므로, 그대로 쓰면 회차 누수(Data Leakage)가 생기고 Validation 성능이 실제보다 좋게 나옵니다.
* 따라서 원래 구분 대신 **촬영 묶음(`capture_group`) 단위로 네 역할을 새로 배정**했습니다. 원래 구분 정보(`출처 데이터셋`, `원래 split`)는 삭제하지 않고 manifest 에 그대로 보존합니다.

## 5. 🎯 G00 시간순 블록 분할 예외 규정

Class 6이 집중된 `G00(50장)`은 띄엄띄엄 무작위 추출하지 않고, **촬영 시간순 연속 블록**으로 절단하여 인접 누수를 최소화합니다.
G00 은 **앞 25장은 파만, 뒤 25장은 파+고추**를 찍은 묶음입니다 (박스 안 빨간 픽셀 15% 이상을 고추로 판정 — 0~24번째 고추 0개, 25~49번째 매 장 1~4개). `kimchi_v2` 는 두 구간을 **각각** 같은 비율로 자릅니다:

```text
G00 시간순 50장 (kimchi_v2)
├── 파 구간 01 ~ 25번째
│   ├── 01 ~ 13 (13장) ──> Train
│   ├── 14 ~ 17 ( 4장) ──> Validation
│   ├── 18 ~ 21 ( 4장) ──> Frozen Test
│   └── 22 ~ 25 ( 4장) ──> Bridge Holdout
└── 파+고추 구간 26 ~ 50번째
    ├── 26 ~ 38 (13장) ──> Train
    ├── 39 ~ 42 ( 4장) ──> Validation
    ├── 43 ~ 46 ( 4장) ──> Frozen Test
    └── 47 ~ 50 ( 4장) ──> Bridge Holdout
```

(`kimchi_v1` 은 01~26 Train / 27~34 Val / 35~42 Test / 43~50 Bridge 로 잘라 고추가 Train 에 3개뿐이었습니다.)

### 5.1 G12 배치 단위 분할 (`kimchi_v2`)

G12 75장은 25장씩 세 번 배치를 바꿔 찍었습니다 (사진당 Class 0 박스 수로 구분). 가운데 배치를 Train 으로 보냅니다:

```text
G12 시간순 75장
├── 01 ~ 25번째 (잎 1장씩)   ──> Validation
├── 26 ~ 50번째 (잎 5장씩)   ──> Train      ← 25|26 사이 촬영 간격 165초 (묶음 안 중앙값 30초)
└── 51 ~ 75번째 (잎 2~3장씩) ──> Validation
```

* **가운데 배치를 고른 이유**: 마른 잎 박스가 가장 많아(약 130개) Train 에 마른 잎 모습을 충분히 넣을 수 있고, 앞·뒤 배치가 Val 에 남아 Val 에도 마른 잎(69개)·반점 갈변(49개)이 유지됩니다.
* **경계**: 앞 경계(25|26)는 165초 간격 + 배치 변경, 뒤 경계(50|51)는 배치 변경(잎 5장 → 2~3장)으로 나뉩니다.

### 5.2 G09 배치 단위 분할 (`kimchi_v4`)

`kimchi_v3` 라벨 개정 후 갈변 BBox 256개 중 **207개가 G09(전부 Train)** 에 있어 Val 갈변이 8개뿐이었습니다. 다른 묶음은 갈변이 0~13개라 묶음을 옮겨서는 늘릴 수 없어, G09 마지막 배치를 Val 로 보냅니다:

```text
G09 시간순 75장
├── 01 ~ 25번째 (15:17~15:41, 갈변 10 · 플라스틱 84 등)  ──> Train
├── 26 ~ 50번째 (15:45~16:06, 넓게 썩은 잎만 · 갈변 130) ──> Train   ← 25|26 사이 262초 (묶음 안 중앙값 51초)
└── 51 ~ 75번째 (16:07~16:32, 갈변 67 · 플라스틱 43 · 가지 16 · 벌레 6) ──> Validation
```

* **마지막 배치를 고른 이유**: 갈변과 다른 이물이 섞인 장면이라 Val 의 다른 사진과 성격이 같고, Train 에는 갈변만 찍은 가운데 배치(130개)가 남습니다.
* **경계**: 50|51 사이는 배치 변경(플라스틱 4개 → 43개)입니다. 같은 회차의 같은 썩은 잎을 다시 배치했을 수 있어 Val 갈변 점수가 다소 낙관적일 수 있습니다 (최종 판단은 Frozen Test).

* **정당화 사유**:
  1. 원칙을 엄격 준수할 경우 Val/Test/Bridge에서 Class 6 평가 지표가 완전히 공백(Zero)이 되는 실무적 위험 방지
  2. G00 내 사진들은 조작자가 매번 다른 김치 조각과 이물질을 배치하여 촬영했음이 육안 확인됨
  3. 연속 블록으로 분할하여 경계선 3곳을 제외한 내부 이미지 간에는 누수 최소화

## 6. ⚠️ 알려진 한계 및 발표 Q&A 대응 전략

1. **Q. G00만 예외로 쪼갠 것은 원칙 위반 아닌가요?**
   - **답변**: "원칙은 묶음 단위 분할입니다. 단, 묶음을 완전히 고수할 때 특정 클래스를 아예 평가할 수 없는 치명적 결손이 발생하는 경우에만 엄격히 통제된 1건의 예외를 두었습니다. G00 내부 이미지들은 형태 다양성이 검증되었고 시간순 블록으로 분할하여 경계 누수를 최소화했습니다."
2. **Q. Val과 Test의 클래스 비율이 조금 다른 이유는 무엇인가요?**
   - **답변**: "묶음 단위(회차 단위)로 분할했기 때문에 회차별 이물 집중도에 따라 비율 차이가 발생합니다. 따라서 모델 비교 시 mAP 단일 점수뿐만 아니라 클래스별 mAP 및 Recall 지표를 반드시 교차 검증합니다."
3. **Q. Split 을 동결했다가 왜 바꿨나요?**
   - **답변**: "Baseline 실패 분석에서 Val 의 마른 잎·반점 갈변과 고추가 Train 에 거의 없다는 것을 확인했습니다 (`reports/failure_hypothesis.md` H1·H2). Frozen Test 는 아직 모델로 평가하지 않은 상태에서 Dataset Version 을 `kimchi_v2` 로 올리고 Baseline 을 다시 학습합니다. `kimchi_v1` 은 `--version kimchi_v1` 로 그대로 재현됩니다."
4. **Q. G12 를 Train/Val 로 나누면 누수가 아닌가요?**
   - **답변**: "같은 날·같은 장소에서 같은 실물 잎을 다시 배치해 찍었을 가능성은 있습니다. 그래서 사진 단위가 아니라 배치(25장) 단위로 자르고, 경계는 촬영 간격·배치 변경 지점에 맞췄습니다. 그래도 Val 점수가 다소 낙관적일 수 있어, 마지막 판단은 G12 가 없는 Frozen Test 로 합니다."
