# 2. Class / BBox 기준 정리

> **팀원 모두가 같은 판단을 하기 위한 한 장짜리 약속**입니다. 같은 사진을 사람마다 다르게 라벨링하면 데이터 품질이 흔들리기 때문에 만듭니다.
> 1일차에 회사가 정해 준 Class 와 가이드의 BBox 원칙을 정리했고, **세부 기준(Class 별 범위·여백 수치)은 확정해서 아래 두 문서에 반영**했습니다.
> 자세한 기준: [Class 기준서](../../../class_guide.md) · [BBox 기준서](../../../bbox_guide.md) · [검수표 작성](../../../manifest_guide.md)

## 1. Class — 회사 제공 번호를 그대로 사용

| ID | 이름 | 사용 | 한 줄 기준 | BBox 한 개의 단위 |
|---:|---|---|---|---|
| 0 | 나뭇잎·종이류 | 사용 | 납작하고 얇은 잎 또는 종이 | 잎 1장 / 종이 1조각 |
| 1 | 플라스틱류·돌·금속류 | 사용 | 식물이 아닌 단단한 이물 | 조각 1개 (반사는 포함, 그림자는 제외) |
| 2 | 나뭇가지류 | 사용 | 목질(나무)의 막대·가지 | 가지 1개 (곁가지 포함) |
| 3 | 벌레류 | 사용 | 곤충·벌레의 몸 형태가 확인되는 것 | 한 마리 (다리·더듬이 포함) |
| 4 | 고무장갑 | **사용 안 함** | 발견되면 **지우지 말고 REVIEW** | – |
| 5 | 병해·갈변 | 사용 | 식재료의 변색·병든 부위 | 이어진 변색 덩어리 1개 (여백 허용치 2배) |
| 6 | 파·고추 | 사용 | 파 또는 고추 조각 | 조각 1개 |

### 애매하면 — 단서 3개 중 2개 규칙

두 Class 사이에서 헷갈리면 느낌이 아니라 **눈에 보이는 단서를 셉니다.** 쌍마다 정해진 단서 3개(모양·표면·색 등) 중 **한쪽이 2개 이상이면 그 Class**, 그렇지 않으면(1:1, 단서가 안 보임) REVIEW 입니다.
쌍별 단서 표는 [Class 기준서](../../../class_guide.md) 의 "애매할 때 구분하는 기준"에 있습니다.

| 헷갈리는 것 | 결과 |
|---|---|
| 잎·종이(0) ↔ 파·고추(6) / 잎(0) ↔ 가지(2) / 가지(2) ↔ 파 줄기(6) / 가지(2)·종이(0) ↔ 플라스틱(1) | 쌍 표의 단서 2개 이상인 쪽 |
| 벌레(3) ↔ 반점·양념 덩어리 | 단서 2개 이상 → 3. 0~1개 → 20px 이상이면 그리지 않음, 20px 미만이면 REVIEW |
| 병해·갈변(5) ↔ 그림자·정상 양념 | **체크리스트**: ① 식재료 표면의 색 변화(떼어낼 수 없음) ② 누런·갈색·검은 계열(붉은 양념색 아님)이 **둘 다 예**이고 ③ 주변보다 5~20%p 칙칙하게 어둡다 / ④ 한 곳에 국한된 불규칙 윤곽 중 **하나 이상 예** → Class 5. 아니면 그리지 않음 |
| 고무장갑처럼 보임 | 단서 2개 이상 → 다른 Class 로 바꾸지 않고 REVIEW (Class 4) |

### Class 약속

```text
번호를 바꾸지 않는다 (5→4 같은 재번호 금지)
        ↓
새 번호를 만들지 않는다 (7 = 정상 김치 같은 것 금지)
        ↓
김치는 Class 가 아니다 → 김치에는 BBox 를 그리지 않는다
        ↓
정상 김치 / 김치+대상 / 대상 단독 은 "이미지 유형"일 뿐 Class 가 아니다
```

### Class 4 를 발견하면

```text
자동으로 지우지 않는다
        ↓
REVIEW 로 표시  (상태 = 수정 필요, 발견된 문제 = REVIEW: Class 4 발견)
        ↓
이미지와 BBox 를 직접 확인
        ↓
2명 이상이 확인
        ↓
이유를 비고(수정 내용)에 기록
```

## 2. BBox — 5가지 약속

```text
1. 객체 전체를 포함한다 (일부를 자르지 않는다)
        ↓
2. 객체 경계에 가깝게 그린다 (배경은 최소로)
        ↓
3. 서로 다른 객체는 BBox 를 따로 그린다 (겹쳐 있어도 구분되면 각각)
        ↓
4. 아주 작아도 종류를 알 수 있으면 빼먹지 않는다
        ↓
5. 애매하면 추측하지 말고 REVIEW
```

### 크기 판정 — 확정 수치 (원본 이미지 픽셀, 네 변 각각)

| 모양 | 판정 | 처리 |
|---|---|---|
| 객체 + 여백이 허용치보다 큼 | 너무 큼 | 수정 |
| 객체 전체 + 여백이 허용치 이내 | **적절** | 검수 완료 (수정 없음) |
| 객체가 BBox 밖으로 4px 이상 나감 | 너무 작음 | 수정 |

| 객체 크기 (BBox 의 짧은 변) | 변마다 허용하는 여백 |
|---|---|
| 40px 미만 | 4px 이내 |
| 40px ~ 200px | 짧은 변의 10% 이내 |
| 200px 초과 | 20px 이내 |

Class 5(병해·갈변)는 경계가 번지므로 위 허용치를 **2배**로 봅니다.

## 3. 검수 상태

> 1일차 초안의 PASS / EDITED / REVIEW 는 팀이 확정한 **검수표의 상태**로 바뀌었습니다. ([manifest_guide.md](../../../manifest_guide.md))

| 검수표 상태 (초안 이름) | 언제 | 예 |
|---|---|---|
| **검수 완료** (PASS) | 기존 라벨이 맞다 (수정 없음) | BBox 위치·Class 모두 정확 |
| **수정 완료** (EDITED) | 고쳤다 | 빠진 이물 BBox 추가, 틀린 Class 변경, 크기 수정, 불필요한 BBox 삭제 |
| **수정 필요** + `REVIEW: 이유 코드` (REVIEW) | 판단이 어렵다 | Class 4 처럼 보이는 것, 정체를 모르는 물체 |
| 검수 전 / 제외 | 아직 안 봄 / 팀이 합의해 뺀 것 | |

```text
애매함 → REVIEW → 다른 사람이 확인 → 2명 이상 합의 → 결정과 이유를 기록
```

## 4. 이미지 유형별 처리

| 이미지 | 처리 |
|---|---|
| 김치 + 대상 객체 | 대상 객체의 BBox · Class 를 확인 |
| 정상 김치 (BBox 없음, 빈 TXT) | 이미지를 보고 이물이 **정말 없으면 빈 TXT 유지 = 검수 완료** / 이물이 보이면 BBox 추가 = 수정 완료 / 애매하면 REVIEW |
| 대상 객체 단독 | 김치가 없어도 **삭제하지 않고** BBox · Class 를 확인 |

## 5. 좌표 형식 (YOLO TXT 한 줄)

```text
class  x_center  y_center  width  height          (한 줄 = 객체 1개, 모두 0~1 비율값)
예) 2 0.7565 0.1623 0.0474 0.0616
```

- 이미지 왼쪽 위가 (0, 0), 오른쪽으로 갈수록 x 증가, 아래로 갈수록 y 증가
- 프로그램은 내부에서 **원본 이미지 픽셀 좌표**로 관리하고, 저장할 때만 비율값으로 바꿉니다

## 6. 확정한 기준 (1일차에 합의가 필요했던 3가지)

| 질문 | 확정 |
|---|---|
| "너무 크다"의 기준은? | 객체와 BBox 변 사이 여백이 위 표의 허용치(작은 객체 4px / 10% / 큰 객체 20px, Class 5 는 2배)를 넘으면 너무 큼 |
| 이미지 가장자리에 걸친 객체는 어떻게 그리나? | **화면에 보이는 부분까지만** 그린다. BBox 는 이미지 밖으로 나가지 않으며, 프로그램이 이미지 경계에서 자동으로 잘라 준다 |
| 가장 작아도 BBox 를 만드는 크기는? | 프로그램은 원본 기준 **4px 미만**은 만들지 않는다. 짧은 변이 **20px 미만**이면서 무엇인지 알 수 없으면 `REVIEW: too_small_to_identify` |
