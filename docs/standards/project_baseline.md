## 3. 공통 데이터 기준

- 전체 이미지: 900장 (JPG) + YOLO TXT 900개, 짝 900 / 900
  - 이물검출_학습데이터1 / train: 500 · 이물검출_학습데이터2 / train: 220 · 이물검출_학습데이터2 / validation: 180
- 번호는 프로그램 화면의 `N / 900` 과 같다. (데이터셋 → split → 파일명 순: 1~500 · 501~720 · 721~900)
- Label Format: YOLO Detection TXT (`class_id x_center y_center width height`, 0~1 비율값)
- Class: 0~6 (회사 제공 번호 그대로, 재번호 금지) — 설정 파일 `configs/classes.yaml`
- Class 4(고무장갑): 사용하지 않음 (발견 시 삭제하지 않고 REVIEW). 실제로 한 개도 없다
- 기존 `train / validation` 구분과 데이터셋 출처는 **기록으로 유지**한다 (검수표의 `출처 데이터셋`·`원래 split` 칸). 검수는 합치지 않고 데이터셋별로 했고, `train / validation` 을 다시 나누는 것은 교과 8 에서 한다

### 1일차 — 데이터 이해 · 기준선 · 설계 · 첫 End-to-End

- **목표**: 데이터와 보안을 확인하고, 팀 기준선을 정하고, 만들 프로그램을 설계한 뒤 사진 1장으로 열기 → 저장 → 다시 불러오기까지 한 번 돌려 본다.
- **정한 것**: 회사 데이터(NDA)는 Git 에 올리지 않는다 · RAW(읽기만) → WORK → FINAL 분리 · 900장 구성(500 / 220 / 180) · Class 0~6 그대로, Class 4 미사용 · BBox 5가지 약속 · 빈 TXT 는 오류가 아닐 수 있다 · BBox 는 원본 픽셀 좌표로 기억하고 화면에만 배율을 곱한다 · 기능 하나씩 구현 → 실행 → 커밋.
- **검수표 확정**: 초안(14칸)을 팀이 정한 19칸 검수표로 바꿨다. 상태 5종, REVIEW 표시 규칙, 자동 기록 칸과 사람이 적는 칸의 구분. ([검수표 작성 기준](manifest_guide.md))
- **만든 것**: 프로젝트 구조, Class 설정 읽기, YOLO TXT 불러오기·저장, RAW 보호와 WORK 저장 경로, BBox 생성·선택, 데이터 조사, 이미지 1장 라벨링 화면, 자체 점검, 저장할 때 검수표(CSV) 자동 기록, Project Baseline · Class 기준서 · BBox 기준서 · README.
- **결과**: 1장 End-to-End 에서 같은 위치 복원, 원본 TXT 불변 (가짜 샘플 기준).
- **막혔던 점**: BBox 선택 시 프로그램이 멈춤(선택 신호 반복) → 이미 선택된 항목이면 무시 · 휠·드래그가 느림(4K 전체를 매번 줄임) → 이미지와 BBox 를 따로 그림.
- **2일차로 넘긴 것**: 실제 데이터 사진 1장 End-to-End, 팀원 역할 확정, 기준서 수치 합의, 조사표 사진 보기.

| ⑤ 지혜성 | 900장 무결성 검증(`validate_dataset`)과 결과 창, 검증 시험 11종, 폴더 열기·A/D 이동, 시험 보고서 |

- **정한 것**: 로직은 각자 파일에 쓰고 `main_window.py` 에는 연결 몇 줄만 추가해 충돌을 줄인다 · 만든 사람과 시험하는 사람은 다르게(② ↔ ③, ④ ↔ ⑤) · 저장 실패하면 이동하지 않는다 · 좌표·저장 오류가 남아 있으면 900장 본 작업을 시작하지 않는다.
- **Daily Gate**: 12개 항목을 구현자·시험자로 나눠 코드와 자동 시험으로 확인했다. (실제 데이터 900장은 4일차 검수에서 사람이 확인했다)
- **발생한 문제**: `main_window.py` 를 여러 명이 고쳐 겹침 → 한 기능으로 합침 · 방향키를 누르면 사진이 쌓여 멈춤 → 연속 입력을 묶음 · WSL 에서 한글 입력 불가 → 조합기 추가.
- **3일차로 넘긴 것**: BBox 이동·크기 조절, Diff 보기, 저장 후 다음(`W`), Validation·Manifest 안정화, Pilot Test.

### 3일차 — 편집 보강 · 안정화 · 사용성

- **목표**: 2일차에 미룬 것을 마무리하고, 900장을 실제로 검수할 때 편하고 안전한 도구로 다듬는다.
- **만든 것**
  - BBox 이동·크기 조절(흰 네모 핸들 8개), 선택 BBox 좌표 실시간 표시, 전체 삭제, 키보드 조작(`Tab`·`Shift+방향키`·`H`)
  - 원본(RAW)과 비교하는 Diff 보기 — 추가·수정·삭제를 색으로 구분
  - `W`(저장 후 다음), 십자선, 밝기·대비·흑백 보정, 툴바 정리, 마지막 폴더·사진에서 이어 시작
  - 상태별 보기 필터('수정 필요'만 모아 보기), 라벨 표(No · 클래스 · 위치 · 상태), 하단 미리보기 줄
  - 한 키 검수: `Enter`(검수 후 다음) · `R`(수정 필요) · `N`(다음 미작업), 말풍선·단축키 도움말(`F1`)
  - 화면 디자인 체계(`theme`), 한/영 키로 한글 전환
- **렉 해결**: 방향키를 꾹 누를 때 하단 미리보기가 원인이었다. 사진 읽기를 다른 스레드로 옮기고 미리보기를 지연 로드해, 키 입력 지연 최대 168ms → 39ms.
- **검수표 점검**: 빈 파일·머리글이 다른 파일, `검수일` 칸이 항상 비던 문제(상태 변경 시 오늘 날짜 자동 기록), 경고창이 사진마다 반복되던 문제를 고쳤다.
- **시험**: 자동 시험 22개 파일 통과, 실제 900장 읽기 전용 점검(짝 900/900, 빈 TXT 0, Class 4 없음, Validation 0건, 읽기→저장→읽기 900/900 일치, RAW 불변).
- **발견해서 고친 오류**: 필터 결과가 없을 때 번호 어긋남 · 대문자 `.JPG` 사진 이동 실패 · BOM 붙은 라벨 첫 줄 읽기 실패 · 메시지가 금방 사라짐 · 시험이 만든 임시 폴더가 디스크를 채움 등.
- **남긴 규칙**: Pilot Test 와 Validation 오류 0건을 확인하기 전에는 900장 본 작업을 시작하지 않는다.

### 4일차 — 900장 교차검수와 결과 합치기 (2026-10-07)

- **목표**: 팀원 6명이 각자 PC 에서 작성한 라벨과 검수표를 모아, 작성자가 아닌 사람이 900장을 모두 검수한다.
- **어려웠던 점**: 라벨(TXT)과 검수표(CSV)가 PC 마다 따로 쌓여, 메신저로 주고받다 보니 파일이 겹치거나 덮어써지고(같은 이름의 CSV, 윈도우의 `Zone.Identifier` 파일), 어느 PC 의 라벨이 최신인지 알기 어려웠다.
- **만든 것**
  - 팀원 라벨을 `data/work` 로 가져오기(`import_labels`), 팀원 검수표를 하나로 합치기(`merge_manifests`, 충돌 규칙·자동 백업·출처 바로잡기)

  - 같은 와이파이 안에서 zip 을 내려받고 올리는 임시 서버(`share_server`) — 4자리 PIN, 사설 IP 만, 검수자·PM 단계별 가이드, 끌어다 놓기 올리기
  - 검수 배정과 진행 방법 문서, 라벨 합치기·결과 주고받기 문서
  - 이미지 유형이 비어 있으면 `Enter` 와 검수 기록 저장을 막는 규칙
- **진행**: 김동훈 1~300 → 지혜성 551~600 → 이후영 301~500 → 지혜성 601~900 → 김동훈 501~550 순으로 결과가 올라왔다. 각자 범위만 골라 합치고(옛 라벨이 최신을 덮어쓰지 않게), 전체본을 다시 만들어 배포했다. 검수자 칸이 비었거나 검수 전으로 남은 4장, 판단 어려움 1장, 너무 작은 BBox 1개를 확인해 정리했다.
- **발견해서 고친 오류**: 출처가 잘못 적힌 401줄이 합치기에서 조용히 빠짐 · 검수자가 원본 라벨을 보고 있었음(라벨 가져오기가 다른 내용을 건너뜀) · 공유 페이지의 끌어놓기 안내가 사라지지 않음 등. ([Test Report](../../reports/test_report.md) §2-1)
- **결과**: 900장 모두 검수 완료(검수 완료 674 · 수정 완료 226), 미처리 REVIEW 0, Validation 오류 0. (§5)

## 5. 검수 기준과 결과

### 상태와 REVIEW

| 상태 | 뜻 |
|---|---|
| 검수 전 | 아직 보지 않음 |
| 검수 완료 | 확인했고 원본 그대로 둠 |
| 수정 완료 | 원본과 달라지게 고쳤음 |
| 수정 필요 | 판단이 필요함. REVIEW 는 `상태 = 수정 필요` + `발견된 문제 = REVIEW: 이유 코드` |
| 제외 | 최종본에서 뺌 |

- 검수를 마쳤는지는 **검수자 칸**으로 확인한다. (`Enter` 로 저장하면 원본과 달라진 사진은 `수정 완료` 로 기록되므로, 작성자가 이미 고친 사진도 `수정 완료` 가 된다)

- 판단하기 어려운 BBox 는 임의로 그리지 않고 REVIEW 로 남긴다. (예: `too_small_to_identify`, `class_ambiguous`) 자세한 기준은 [BBox 기준서](bbox_guide.md) · [Class 기준서](class_guide.md)
- REVIEW 최종 판단: 팀장(PM)과 해당 검수자가 판단한다. 최종 미처리 REVIEW 는 0건이고, REVIEW 이력이 있던 2장(180번 · 601번)은 지혜성 · 김석범이 확인했다 ([이슈 기록](../records/이슈기록.md))

| 900장 전체 검수 완료 | **달성** — 검수자 칸 900줄 모두 기록, 작성자와 검수자가 같은 줄 0 |
| FINAL 데이터 정리 완료 | **달성** — `data/final/` 이미지 900장 + 라벨 900개 (`tools/build_final.py`) |
| 교과 8 사용 가능 | **달성** — [QA Summary](../../reports/qa_summary.md) 최종 판정, [Handoff](../handoff/subject08_handoff.md) 최소 확인 8항목 통과 |

> 숫자는 검수표와 `data/work` 를 읽어 센 값이다. 라벨을 더 고치면 `python tools/build_final.py --apply --overwrite` 로 최종본을, `python tools/qa_summary.py --apply` 로 QA Summary 를 다시 만든다.
